🧠 Concepts, in plain English

What this whole project is about

Using one AI assistant is simple. The moment you use several at once on the same job, three new problems show up that don't exist with just one: they can duplicate each other's work, they can step on each other's changes, and nobody automatically knows when a human needs to approve something risky before it happens. This course walks you through each problem on purpose, then teaches the standard fix.

The 16 Pillars — your reference checklist

Every design decision in this course traces back to one of these. You don't need to memorize them — just be able to point at a system and say which ones it covers.

#PillarPlain-English meaning
1Shared stateEveryone reads/writes the same notepad, so nobody works from a private, wrong picture.
2Task allocationWork goes to whoever's actually suited for it, not just whoever's fastest to grab it.
3Team designBoss-led, assembly-line, or flat group — the shape has to fit the job.
4Result sharingFinished work gets posted with "who made this," so it's not silently redone.
5CommunicationMessages say what to do, not just what happened.
6NegotiationConflicts get resolved by a rule, not by both sides quietly doing their own thing.
7Goal persistenceStays on task instead of wandering off and "improving" everything it notices.
8MemoryA lesson learned today isn't forgotten tomorrow.
9LearningA mistake happens once, not fifty times.
10Human-in-the-loopGraduated levels of "check with me first" — never a rubber stamp.
11Embodied agentsReal-world physical limits the model can't reason around.
12TrustNew team members earn trust over time; being new ≠ being unreliable, but it does mean closer watching at first.
13GovernanceHard rules that can't be talked around, even by a clever request.
14SimulationTest the bigger, messier version before it happens for real.
15EvaluationGrade the teamwork, not just whether the output looks fine.
16FrameworksKnow what a tool actually solves before reaching for it.

🔧 Git terms explained (the ones that tripped us up)

origin
A pointer to where your project lives online (GitHub). It's a location, not a version.
main (formerly "master")
The name of the primary timeline inside your repo. A branch, not a location. One origin can hold many branches.
create (in gh repo create)
The action word — "make a new one." Whatever comes right after it is just the name you're assigning, not a second instruction.
local vs. online copy
Your local folder and the GitHub repo are two separate copies that you deliberately keep in sync with push (local → GitHub) and pull (GitHub → local). Naming them the same thing is a convenience, not a requirement.
add (staging)
Marking a changed file as "include this in my next save point." Like putting an item in a cart before checkout. Produces no output when it works.
commit
The actual save point — a permanent snapshot with a note attached, saved to your local history.
push
Sends your saved snapshots from your computer up to GitHub, so the online copy catches up.

🤔 .gitignore: how to decide (not a list to memorize)

Don't memorize a list of filenames — ask three questions about any file, and the answer falls out on its own:

QuestionIf "yes" →Example
1. Regenerable? If this vanished right now, would it come back automatically (a build/install command recreates it), or is real work gone forever?Ignore itnode_modules/, dist/ — both rebuild from a source file you do track
2. Secret? Does it contain a password, API key, or token?Ignore it, no exceptions — even in a private repo, history is forever.env
3. Personal preference? Is this specific to your own machine/editor, not shared project work?Ignore it.vscode/, .DS_Store

If the answer to all three is "no" — a human deliberately wrote it, it's not a secret, and it's not just your personal setup — track it. That's a real project file (e.g. src/index.js).

The nuance: "but my team needs this config"

Real-world wrinkle we worked through: a .env file often holds settings a whole team needs (like which database to connect to), not just secrets. The fix isn't to track the real file — it's to separate the shape from the value:

  • .env — the real file, real secret values (DB_PASSWORD=actualSecret123). Always ignored.
  • .env.example — same variable names, fake/blank placeholder values (DB_PASSWORD=your_password_here). This one is tracked and committed, so teammates know what config exists without ever seeing a real secret.

Rule of thumb: share the structure, never the secret.

Module 1 — Single-Agent Baseline

Concept

Before feeling the multi-agent crisis, prove that one well-prompted AI assistant, with a clear role, already ships clean work on a small real codebase.

Requirement

Pick a small imperfect codebase. Write a role prompt (ROLE.md) and 2–3 scoped tickets. Run one Claude Code session through them end to end.

Checkpoint

Did it stay in scope? Is the role prompt specific enough that a different agent reading it would behave the same way?

Module 2 — Shared State / The Blackboard

Concept — Pillars 1 & 4

Three identical agents, one shared markdown file, no coordinator. Watch duplication, races, and a synthesis bottleneck appear.

Requirement

A shared brief (task.md), an empty blackboard.md, and a CLAUDE.md protocol: append-only writes, read-before-you-research, one agent writes the final synthesis.

Checkpoint

Write a POSTMORTEM.md diagnosing exactly where duplication and idle time happened, and which pillar was missing.

Module 3 — Task Allocation

Concept — Pillar 2

Fix "first agent to notice grabs it" with atomic, capability-based task claiming — a tiny CLI with a real file lock.

Requirement

Build task-cli backed by tasks.json, with an exclusive-lock file so two agents can never both claim the same task. Round 1: first-claim. Round 2: capability-gated.

Checkpoint

Show the lock code and a test proving two simultaneous claims never both succeed.

Module 4 — Team Design (Topology)

Concept — Pillar 3

Same brief, three team shapes: supervisor (one delegates + integrates), pipeline (strict sequential handoff), swarm (capability-aware peers).

Checkpoint

A comparison table (time, quality, single-point-of-failure risk) and a justified pick for which topology you'd actually use in production.

Module 5 — Human-in-the-Loop & Governance

Concept — Pillars 10 & 13

HITL (every step) / HOTL (exceptions only) / HOOTL (outcomes only). A gate agent routes proposals by risk; a governance floor blocks some actions no matter what the AI argues.

Requirement

Build hitl-cli + gate-policy.md. Run normal scenarios, then adversarial ones (prompt injection, high-stakes requests) and see what gets through.

Checkpoint

Find one adversarial proposal that got through when it shouldn't have — if none did on the first try, the test wasn't adversarial enough.

Module 6 — Capstone Build Sprint

Concept — Pillars 1, 2, 3, 4, 5, 9, 15

Three role-specialized agents ship real code using typed messages ([REQUEST] [INFORM] [COMMIT] [BLOCK] [ESCALATE] [LESSON]), atomic task claims, and stigmergic learning.

Git angle

Add a GitHub Actions workflow that runs your eval-self.sh on every PR — GitHub becomes the automated evaluator, not just a commit log.

Checkpoint

L1/L2/L3 eval output, one [LESSON] that changed downstream behavior, and a green CI check.

Bonus — Dynamic Agent Registry

Concept — Pillars 2 & 3, abstracted

A registry of agent types (not fixed instances), each with capabilities and a spawn/reap rule, matched against a backlog by an orchestrator loop: SCAN → MATCH → SPAWN → CLAIM → PUBLISH → REAP → REPEAT.

Checkpoint

A hand-traced timeline for a toy backlog, including one capability collision worked through.

Final — Polish & Publish

Write the real README, update PROJECT.md with your own "what NOT to do" notes, tag a release (v1.0), and consider going public once you're happy with it.

📖 Glossary

Blackboard
Shared file/store every agent reads and writes — the simplest form of shared state.
Contract net
Task-allocation protocol: tasks announced, capable agents matched — not first-come.
Performative
A typed message tag (REQUEST, INFORM, COMMIT...) that encodes intent, not just text.
Stigmergic learning
Agents coordinate indirectly by leaving traces in the environment (a "lesson" note) rather than talking directly.
HITL / HOTL / HOOTL
Human-in / on / out-of-the-loop: approve every step / approve exceptions only / review outcomes only.
Provenance
A result tagged with who produced it and from what inputs, so it can be trusted or challenged.
Topology
The shape of who talks to whom: supervisor (hub), pipeline (chain), swarm (mesh).
